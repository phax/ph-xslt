# Performance batch 1 (2026-11-08)

Baseline `43a7f25` against `5c1d66a`, measured with `xslt-benchmark/compare.sh 43a7f25 5c1d66a -f 2 -wi 3 -i 5 -prof gc`
on an Apple M5, Temurin 21.0.13, while the machine was in use (load average 5 to 9). Timing differences below about
10 % are noise; the allocation per operation (`gc.alloc.rate.norm`) does not depend on the load. Workloads whose time
looked worse while their allocation was the same or lower (parse, streaming buffered, `rules`, `child`) were measured
again with the order of the commits swapped: there the baseline was equal or slower (parse at 10,000 lines 23.1 ms
against 19.6 ms), so the order of the runs, not the change, caused it.

The changes of the batch (see `docs/PLAN.md`, "Function calls, conversions and key patterns"):

* XSD 1.1 assertions: one `XdmSchemaType` per type and validation run instead of one per annotated node.
* `xsl:number`: linear counting (name index and binary search on document order for `level="any"`, the child index
  for `single`/`multiple`, constant `format` and `start-at` analysed at compile time).
* The default collation resolved once per static context (`min`, `max`, `distinct-values`, `index-of`, `deep-equal`,
  `sort`, `array:sort`).
* One shared, read-only default function library; each stylesheet registers into a child library.
* The selecting axis of a pattern's last step computed once per pattern.
* Duration parts with `long` arithmetic instead of `BigInteger`.
* No capturing lambda per name in the tree builder and the stream reader.
* `EAtomicType.isDerivedFrom` and `isNumeric` in constant time.

partly noise: no change of the batch touches the regular expression code directly; the collation and type checks are
on its path.
