# Baseline of the performance phase (2026-11-06)

First run of `xslt-benchmark` (see its [README](../../xslt-benchmark/README.md) for the workloads) against `main`
`6b8e1c2`, followed by a JFR profile of every workload. Measuring only: nothing was changed in the engine.

## Set-up

- Apple M5, 10 cores, 24 GB; macOS; Temurin 21.0.13. The machine was in normal desktop use (WindowServer, Word, a
  terminal): load average 1.5 to 2.1 during the run (12:22 to 12:31).
- JMH 1.37, average time, 3 warm-up and 5 measurement iterations of 1 s, 1 fork, `-Xmx3g -Xss8m`, `-prof gc`. The
  whole run took 8.5 minutes.
- Profiles: `MainProfile <group> <case> <lines> 12` with `-XX:StartFlightRecording=settings=profile`,
  `stackdepth=256`, `-XX:+DebugNonSafepoints`; 10,000 lines (100,000 for streaming, 2,000 for `number`). Shares are of
  the execution samples of the threads `main`, `ph-xslt-compile` and `ph-xslt-transform`. "Inclusive" counts a method
  once per sample in which it is on the stack, "self" only when it is the top frame.
- Document: 1,000 lines are 10,005 elements, 3,079 attributes, 19,009 text nodes (11 whitespace-only per line) and
  303 KB; 10,000 lines 320,699 nodes and 3.0 MB.

Observations:

- Everything except `positional` and `number` is linear in the document (10,000 lines take 9.1 to 12.8 times as long
  as 1,000).
- `xsl:number` is quadratic: twice the lines take four times as long (and allocate four times as much). 10,000 lines
  would take about 45 s.
- `positional` is linear in the lines but costs 2.8 ms per numeric predicate over 10,000 children: the predicate is
  evaluated for every candidate (2 million evaluations of `max((1, $i * $c idiv 200))`).
- XSD 1.1 costs 2.9 times XSD 1.0 for one assertion per line, one assertion facet per price and one type alternative
  per tax element.
- Streaming is 23 % faster than buffered at 100,000 lines and 11 % slower at 10,000; both allocate the same (11.8 KB
  per line, 2.8 times a plain parse).
- Parsing allocates 132 bytes per node (14 bytes per input byte), of which 5.6 % are lambdas of
  `XdmTreeBuilder._getName` (the capturing `computeIfAbsent` lambda is created for every name, also for known
  names). The retained size per node is measured by `xdm-memory-benchmark` (element 72 bytes, attribute 56, text 48,
  child lists with room for 10).

## The known candidates against the profile

| Candidate (PLAN) | What the profile shows | Verdict |
|---|---|---|
| Child scan in `AxisNavigator.collectNamedChildren` | 71 % (child), 26 % (rules), 22 % (arithmetic, grouping), 19 % (iterate), 13 to 15 % (strings, regex, predicate); `getChildAtIndex` and the name comparison of differing names are most of it | confirmed, the widest hot spot; the per-line elements have 19 children of which 11 are whitespace text |
| Key index `HashMap` growth | `HashMap.resize` 0.7 % in keys; the index build (53 %) is the evaluation of `use` per node | not worth it; the build per transformation is the cost |
| Context allocation per call and focus | `DynamicContext.with*` + `XsltContext.with*` 5 to 9 % in recursion, iterate, maps, dispatch; 6 + 4 % of the bytes in identity | confirmed, moderate |
| `EAtomicType.isNumeric` via `isDerivedFrom` | `isNumeric` 1 to 4 % inclusive; `isDerivedFrom` itself 3 to 8 % self in most XPath workloads (exists 8 %, recursion 5.6 %, predicate 5.3 %), from many callers | confirmed, and wider than `isNumeric`: make the derivation test constant for all callers |
| `xsl:number` context per candidate (`NumberInstruction`) | the context is 2.5 %; the cost is the quadratic counting (`_countAny` 93 %, a subtree list per preceding sibling) | confirmed as a hot spot, but the fix is the algorithm |
| `array(T)` checks without memo (`SequenceTypeMatcher`) | iterate is linear (5.2 ms for 10,000 lines); `SequenceTypeMatcher` already uses `XdmArray.getUniformMemberType` | already done, drop |
| Memory per node | parse allocates 132 bytes per node; 5.6 % of it are name-lookup lambdas; streaming allocates 2.8 times a parse per line | open; needs `xdm-memory-benchmark` for the retained part |

New hot spots that were not on the list:

1. `XdmSchemaType.of` per annotated node in XSD 1.1 assertions (68 % of the 1.1 validation).
2. `FunctionLibrary.createDefault` per compiled stylesheet (47 % of compiling).
3. `PatternMatcher._getSelectingAxis` recomputed on every `canMatch` (26 % of dispatch, 20 % of number).
4. The default collation resolved from its URI on every call of `min`/`max` (54 % of positional).
5. Focus-independent numeric predicates evaluated per candidate (positional).
6. `days-from-duration` through `BigInteger` division (33 % of flwor).
7. `SequenceTypeMatcher.convert` of arguments and parameters is still 16 to 23 % in strings, regex, grouping, iterate,
   recursion and maps.
8. `XdmSequence$Builder` 10 to 12 % self in predicate, exists and positional.

## Recommendation: what to fix first

Ranked by impact (time saved on the workloads, how common the shape is) against risk (how much of the model or the
semantics it touches):

1. **Cache the schema type of built-in and compiled types in XSD 1.1 assertions** (`XsdValidationRun.getAssertSchemaType`,
   `XdmSchemaType.of`/`findBuiltinAtomicType`). Up to 68 % of 1.1 validation, so roughly 1.1 at the cost of 1.0
   plus the assertions themselves; local change, no semantics. High impact, low risk.
2. **`xsl:number` counting in linear time**: `level="any"` from the document order (the name index for count patterns
   with final names, as S8 does for keys; otherwise one walk in reverse document order without the subtree lists),
   and a memo of the last counted sibling for `single`/`multiple`. Quadratic to linear (1.8 s at 2,000 lines); the
   W3C `number` tests guard the semantics. High impact on numbering stylesheets, medium risk.
3. **Compute the selecting axis of a pattern's last step once** (`PatternMatcher._getSelectingAxis` /
   `canLastStepSelect`, per pattern and node kind at compile time). 20 to 26 % of template dispatch and numbering,
   which every apply-templates stylesheet pays. Medium-high impact, low risk.
4. **Share the default function library** instead of `FunctionLibrary.createDefault` per stylesheet (an immutable
   parent library, the stylesheet functions in a child). About half of compile time; matters for hosts that compile
   many stylesheets (Schematron). Medium impact, low risk (the modification stamp of S8 already exists).
5. **Child steps from small elements** (`collectNamedChildren`): the widest hot spot (13 to 71 % in most XPath and
   XSLT workloads), but the fix that removes it (element-only child arrays or integer name codes per node) changes the
   node model and the memory per node; first try the cheap part (skip text nodes before comparing names, no
   `XdmQName.equals` on different local names). High impact, higher risk; plan it with the memory work.

Smaller, low-risk items for later: resolve the default collation once per static context (positional 54 %); make
`EAtomicType.isDerivedFrom` constant (3 to 8 % self everywhere); `days-from-duration` without `BigInteger`; the
`XdmTreeBuilder._getName` lambda per name.
