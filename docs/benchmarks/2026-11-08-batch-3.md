# Performance batch 3 (2026-11-08)

Batch 2 (`9f793e3`) against `11d0d37`, measured with `xslt-benchmark/compare.sh -f 1 -wi 3 -i 5 -prof gc` at 10,000
lines for every workload, in both orders of the commits (load average 3 to 8). The two orders agree on every
workload; time is the mean of both runs.

The changes of the batch:

* `XdmSequence` holds a single item without an array, builders hand their buffer over instead of copying it,
  `XdmSequence.ListBuilder` replaces the list-then-copy of axis steps and index lookups, literal sequences are built
  once (`LiteralExpr.sequence ()`).
* `FunctionCallSite` keeps the literal arguments converted for the resolved definition.
* `normalize-space`, `upper-case` and `lower-case` return unchanged strings without a copy; `concat` is pre-sized.
* Children of documents and elements in a plain array (trimmed when the element is complete) instead of a list; the
  child name scans test the node class directly; `XdmQName.equals` rejects different local names by their hash first.
* The tree builder takes a text node of one character event as its string, shares indentation whitespace per
  document, looks names up in one table, reserves the attribute list; `XdmParser.parse (String)` no longer copies the
  input; the maximum element depth is recorded (`XdmDocumentNode.getMaxElementDepth`), so XSD skips its depth walk.
* `IXdmNode.hasDeclaredNamespaces` and `getDeclaredNamespaceUri` without copying the declarations, used by the
  serializer, the SAX emitter, the XSD assertion trees, node copies and namespace fixup.

Compiling, `xsl:number` and template dispatch are unchanged. Retained heap of the tree (`xdm-memory-benchmark`,
JOL): smaller on every document, e.g. XMark 19.3 to 14.5 MB, iTunes plist 116.8 to 84.8 MB, the XSLT specification
21.4 to 17.9 MB; an element stays 72 bytes.

Since the baseline of 2026-11-06 (`docs/benchmarks/2026-11-06-baseline.md`, measured under a different load, so the
ratios are approximate): `xsl:number` at 2,000 lines 1,797 ms to 3.5 ms, XPath positional 564 ms to 2.1 ms, XPath
strings 7.0 to 3.9 ms, XPath rules 20.3 to 15.8 ms, XSD 1.1 112 to 72 ms, XSLT dispatch 40.1 to 34 ms.

Next in the profiles: in the rules workload `XPathEvaluator.evaluateInternal` (6 %), the output lists of the callers
(`ArrayList.grow` about 5 %), `FunctionLibrary.getModificationStamp` walking the parent chain on every call (2 %),
`DynamicContext.getVariable` as a linear lookup (3 % of recursion), constructors from strings (`xs:decimal`,
`xs:date`, 10 % of rules), argument conversion of untyped nodes to `xs:string?`; the child scan is now bound by
memory latency. Parsing is mostly the JDK SAX parser; in the builder `startElement` (18 %), `getSystemId` per element
in `_applyEntityBase`. Not done: `NonBlockingStringReader` in `XsltCompiler`, `XsltTransformHandler` and
`PackageRegistry`; attributes as a plain array (an element would grow from 72 to 80 bytes).
